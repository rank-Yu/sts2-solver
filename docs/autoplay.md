# 战斗自动执行与核对

[返回文档索引](README.md)

`CombatPilot`（`src/Core/Autoplay/CombatPilot.cs`）负责一整场战斗：等到出牌阶段就请求搜索，按路线逐个动作执行，每一步都核对实际结果，偏了就重搜。它本身不碰游戏对象，所有原生操作都通过宿主接口 `ICombatPilotHost` 完成，所以同一套循环既能在游戏里跑，也能在离线工具里跑。

## 宿主

| 场景 | 宿主 | 执行方式 |
| --- | --- | --- |
| 游戏 Mod | `CombatPilotHost` | 原版动作队列与选牌入口，逐动作导入核对 |
| 内核离线评测 | Differential 的离线战斗宿主 | 在模拟内核里执行路线，只用于质量和性能评测 |
| 原版动作对照 | Differential 的 `NativePilotHost` | 用原版入口执行，并检查原生终局 |

内核回放通过不等于原版动作对照通过，两类报告要分开写。

## 一条路线的生命周期

1. 主线程导入当前状态，编译出只含冻结数据的搜索请求。
2. 后台跑组合搜索（见 [战斗搜索](combat-ai.md)）。完成后用模拟内核把选中的路线重放一遍，得到每个动作前后的预期状态和选牌信息。
3. 主线程通过游戏入口出牌、喝药、结束回合。
4. 每个动作完成后重新导入实际状态并和预期比较。一致就继续；不一致就丢掉剩下的路线，从实际状态重搜。
5. 到了新回合，如果状态和预测一致、路线还有剩余动作，就接着用原路线，不重搜。

## 执行与核对（游戏 Mod）

出牌、喝药和结束回合都走原版动作队列；选牌通过原版的 `ICardSelector` 接口作答。执行前先核对回合、能量、牌的身份、目标和可用性；选择的数量和选项必须和游戏当前的实际请求一致，对不上就不猜。

每执行完一个动作，等游戏把动作队列跑空，再把当前战斗重新导入成 `Battle`（`LiveCombatTracker`），和预期状态逐字段比较：HP、格挡、能量、牌堆顺序、Power、遗物、药水、随机数、计数和胜负。只有游戏里观察不到、或之后不可能再被读到的字段会先归一化再比，规则写在 `BattleReconciler`。不会为了让比对通过而放宽容差。

## 什么时候停

- 搜索失败、返回空路线或重放无效时，不执行半成品路线。
- 同一回合连续 3 次部署失败或出现偏差，暂停并交还手动控制（`MaximumConsecutiveFailures`）。
- 搜索结果是 `CapacityBounded`（状态超出容量，见 [战斗搜索](combat-ai.md#7-内存与容量)）时立即暂停：从同一状态重搜还会撞上同一个容量，重试没有意义。
- 回合数超过 200 时暂停（`MaximumTurns`）。

## 取消

再按一次 F8、战斗结束或退出场景时，取消搜索和自动执行。已经入队的游戏动作会执行完，取消在稳定边界生效。测试清理会等 worker 和自动战斗会话都退出后才切换场景。

## 配置注入

`CombatPilotHost` 可以接收一个在主线程上调用的策略配置函数，测试侧用它设置固定的请求参数。生产代码不接收测试场景 DTO，也不依赖 TestHost。搜索热路径不读取任何全局设置，配置只能在捕获请求时注入。
